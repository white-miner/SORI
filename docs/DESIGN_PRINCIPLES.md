# SORI Design Principles

> **SORI는 현실의 고객 파일철을 꺼내 기록하고 다시 정리하는 직관은 그대로 유지하면서, 검색·분류·연결·속도는 디지털 수준으로 확장한 뷰티 현장용 고객 기록 시스템이다.**

이 문서는 SORI의 모든 화면, 기능, 컴포넌트, 상호작용을 판단하는 최상위 디자인 기준이다.

새 화면·새 기능·새 UI를 만들기 전에 이 문서를 먼저 확인한다. 아래 원칙을 만족하지 못하는 구현은 코드가 동작하더라도 SORI의 디자인으로 승인하지 않는다.

---

## 1. 기본 전제

SORI는 일반 CRM, 일반 예약 앱, 일반 데이터베이스, 일반 입력폼이 아니다.

SORI는 실제 현장에서 사용하는 다음의 공간과 행동을 디지털로 옮긴다.

```text
서랍
→ 고객 파일철
→ 방문 기록지
→ 사진·동의서·결제 문서
→ 다음 방문 메모
```

사용자는 앱 사용법을 새로 배워서는 안 된다. 화면을 한두 번 보고 만져보면, 현실에서 고객 파일을 찾고 종이에 기록하고 파일철에 문서를 끼워 넣는 방식이 자연스럽게 이해되어야 한다.

```text
설명으로 배워야 하는 앱이 아니라
구조를 보는 순간 이해되는 앱
```

## 2. 최상위 원칙

### 2.1 UI 완성이 최우선이다

현재 SORI 개발의 최상위 법칙은 UI 완성이다.

```text
UI 완성
> UI 상호작용
> 시각적 일관성
> 기능 연결
> 데이터 정교화
```

데이터는 실제 운영과 함께 쌓이고 나중에 정교화할 수 있다. 반면, 잘못된 디자인은 시간이 지나도 저절로 좋아지지 않으며, 기능이 추가될수록 더 큰 비용으로 굳어진다.

따라서 UI 작업을 아래 이유로 중단하거나 뒤로 미루지 않는다.

```text
영구 번호 발급
DB migration
backfill
SSOT 완결성
RLS
Storage 재구성
서버 동기화 고도화
```

UI 검증 단계에서는 임시 데이터, fixture, 화면용 번호를 사용할 수 있다. 단, 사용자가 실제로 보게 될 화면의 품질 기준은 최종 수준이어야 한다.

### 2.2 현실의 물성과 손의 이동을 번역한다

새 기능을 발명하기 전에 먼저 현실에서 사용자가 무엇을 하는지 확인한다.

```text
무엇을 꺼내는가?
무엇을 넘기는가?
무엇에 라벨을 붙이는가?
무엇을 기록지에 끼우는가?
무엇을 다시 찾는가?
```

그 행동을 화면의 공간 구조와 상호작용으로 옮긴다.

```text
서랍을 찾는다
→ 가로 서랍 index

파일철을 꺼낸다
→ No 고객 파일 label

기록지를 넘긴다
→ Today / vN 기록지 label

종이에 이어 쓴다
→ Paper Record의 inline edit

파일을 색으로 찾는다
→ 끝자리별 index color
```

### 2.3 아날로그 직관과 디지털 즉시성을 동시에 제공한다

SORI는 아날로그 파일철을 흉내 내는 앱이 아니다. 현실 파일철의 장점과 디지털의 장점을 동시에 제공해야 한다.

| 아날로그에서 유지할 것 | 디지털에서 추가할 것 |
|---|---|
| 서랍·파일철·기록지의 공간 위계 | 즉시 검색 |
| 번호와 색 라벨로 찾는 감각 | 키워드 검색 |
| 종이에 기록을 이어 쓰는 감각 | 카테고리·기간·상태 필터 |
| 문서를 파일철에 끼워 넣는 맥락 | 한 번의 탭으로 정확한 기록 위치 이동 |
| 쌓일수록 남는 장기 이력 | 사진·결제·동의·프로그램 연결 보기 |

원칙:

```text
파일철 보기는 기본 Home이다.
검색과 필터는 파일철을 대체하지 않는다.
검색과 필터는 필요한 파일철로 가장 빠르게 이동시키는 렌즈다.
```

## 3. SORI의 네 가지 UI 문법

SORI는 새로운 화면을 만들 때마다 버튼·카드·칩을 임의로 발명하지 않는다. 모든 화면은 아래 네 가지 UI 문법을 중심으로 만든다.

### 3.1 Workspace Folder Tab

사용처:

```text
Desk / Chart / Programs / Flow
```

의미:

```text
앱의 최상위 작업공간 전환
```

규칙:

- 넓고 읽기 쉬운 폴더 라벨이다.
- 선택된 탭은 SORI Purple `#8B5CF6` 배경과 흰 글자를 사용한다.
- 선택된 탭은 주변보다 약간 돌출되어 보인다.
- 선택된 탭은 아래 본문 surface와 한 면으로 이어져 보여야 한다.
- 선택 탭 아래를 rail hairline이 관통하면 실패다.
- 비선택 탭은 translucent white fill과 1dp outline을 사용한다.
- 완전한 rounded rectangle, pill button, 일반 Material TabBar처럼 보이면 안 된다.

### 3.2 File Index Label

사용처:

```text
서랍 A / 서랍 B / ...
신규 / No.1 / No.2 / ...
신규 작성 / Today / v12 / v11 / ...
```

의미:

```text
서랍, 고객 파일철, 방문 기록지의 가로 인덱스
```

규칙:

- button, Material Chip, ListTile, segmented control이 아니다.
- 얇고 넓은 파일 라벨 또는 기록지 라벨처럼 보여야 한다.
- 좌우로 계속 이어지고 가로 스크롤될 수 있어야 한다.
- 선택된 라벨은 현재 열려 있는 본문과 시각적으로 연결된다.
- 각 rail은 위계에 따라 크기와 밀도가 달라야 한다.
- 최상위 Workspace tab과 Chart 내부 file label은 같은 모양을 단순 복제하지 않는다.

### 3.3 Paper Record

사용처:

```text
Chart 본문
상담 기록
고객 메모
방문 기록지
```

의미:

```text
한 장의 기록지를 읽고 이어 쓰는 표면
```

규칙:

- 일반 설정 form이 아니다.
- 큰 rounded TextField가 세로로 반복되면 안 된다.
- 필드는 하나의 긴 종이 surface 안에서 divider와 여백으로 구분한다.
- 기본은 읽기 상태다.
- 사용자가 필요한 섹션을 탭한 경우에만 해당 지점이 inline edit로 전환된다.
- 저장 후에는 다시 기록지의 문장/내용처럼 보인다.
- 저장 action은 기록지 하단 또는 기록 흐름 안에 조용하게 배치한다.

### 3.4 Quiet Action

사용처:

```text
저장
추가
사진
결제
동의서
복제
필터
검색
```

의미:

```text
사용자의 행동을 돕지만 화면의 구조를 지배하지 않는 조용한 행동 진입점
```

규칙:

- 모든 action을 크고 검은 pill CTA로 만들지 않는다.
- action은 현재 문서·파일·기록의 맥락 안에 배치한다.
- 동의서·사진·결제는 고객 파일철의 부속 문서 index로 보이게 한다.
- action이 독립된 버튼 모음처럼 보이면 안 된다.
- 가장 중요한 한 가지 행동만 상황에 따라 강조할 수 있다.

## 4. Chart의 비가역적 구조

Chart는 SORI의 대표 경험이며, 아래 위계를 벗어나면 안 된다.

```text
Chart

서랍 A → 서랍 B → 서랍 C → ...

신규 → No.1 → No.2 → No.3 → ...

Today → v12 → v11 → v10 → ...
또는
신규 작성 → v12 → v11 → v10 → ...

선택된 Chart 기록지
```

### 4.1 위계의 의미

| 단계 | 현실의 대상 | 디지털 표현 | 목적 |
|---|---|---|---|
| 1단 | 서랍 | 서랍 A / B / C rail | 많은 고객 파일철을 담는 상위 보관 공간 |
| 2단 | 고객 파일철 | 신규 / No.1 / No.2 rail | 고객 1명당 하나의 지속 파일 |
| 3단 | 방문 기록지 | 신규 작성 / Today / vN rail | 한 고객 파일 안에 누적되는 날짜별 기록지 |
| 본문 | 종이 Chart | Paper Record | 선택된 기록을 읽고 이어 쓰는 공간 |

### 4.2 번호 규칙

```text
No.N = 고객 파일철 번호
vN = 고객 파일철 안의 방문 기록지 번호
```

- `No`와 `v`는 절대 혼용하지 않는다.
- 고객 이름은 No rail의 주 라벨을 대체하지 않는다.
- 고객 이름은 선택된 파일 header에서 보조 정보로 표시한다.
- 오늘 기록이 있으면 `Today`는 실제 오늘 `vN`의 표시 별칭이다.
- `Today`와 실제 오늘 `vN`을 동시에 rail에 중복 표시하지 않는다.
- 오늘 기록이 없으면 `신규 작성`이 맨 앞의 빈 기록지 label로 표시된다.
- 오늘 기록이 없어도 과거 기록지는 숨기지 않는다.

```text
오늘 기록 없음:
신규 작성 → v12 → v11 → v10

오늘 기록 있음:
Today → v12 → v11 → v10
```

### 4.3 고객 파일 header

선택된 No 고객 파일에는, 방문 기록보다 위에 다음 정보를 짧고 빠르게 읽을 수 있게 둔다.

```text
No.25 · 고객 이름
최근 방문
주의사항
현재 포커스/니즈
다음 행동
```

이 영역은 전체 프로필을 재현하는 곳이 아니다. 오늘 상담 또는 시술 전에 반드시 알아야 할 핵심 맥락만 보여 주는 customer snapshot이다.

### 4.4 부속 문서

고객 파일철에는 아래 문서가 연결된다.

```text
전자 동의서
사진
결제
```

이들은 방문 기록 rail과 구분되는 고객 파일철의 지속 문서다.

- 화면 우측에 떠 있는 action chip 모음으로 만들지 않는다.
- 고객 파일철에 끼워져 있는 document index처럼 보이게 한다.
- 선택하면 기존 동의서·사진·결제 흐름으로 연결할 수 있다.

### 4.5 Chart 기록지 필드

필드 순서는 고정한다.

```text
1. 고객 상태
2. 니즈
3. 상담
4. 제공 서비스
5. 사진
6. 결제
7. 다음 방문 참고
```

모든 방문 Chart는 이 순서를 유지해야 한다. 표준화된 구조는 빠른 읽기와 누적 기록 비교를 가능하게 하지만, UI는 폼이 아니라 한 장의 기록지여야 한다.

## 5. Index Color System

색상은 장식이 아니라, 실제 파일에 색 인덱스를 붙여 빠르게 찾는 경험을 디지털에서 복원하는 탐색 장치다.

### 5.1 기본 끝자리 색상

| 끝자리 | 기본 색상 |
|---:|---|
| 0 | 흰색 |
| 1 | 빨강 |
| 2 | 노랑 |
| 3 | 주황 |
| 4 | 초록 |
| 5 | 하늘색 |
| 6 | 파랑 |
| 7 | 보라 |
| 8 | 분홍 |
| 9 | 회색 |

적용:

```text
No.21 = 끝자리 1 = 빨강 계열
v21 = 끝자리 1 = 빨강 계열
Today가 v21이면 = 빨강 계열
```

### 5.2 색상 사용 규칙

- No와 v는 동일한 0~9 팔레트를 공유한다.
- Today는 실제 오늘 방문 `vN`의 끝자리 색상을 상속한다.
- 신규와 신규 작성은 숫자가 없으므로 SORI Purple을 기본으로 사용한다.
- 선택되었다고 모든 No/v label을 SORI Purple로 통일하지 않는다.
- 선택된 label은 같은 끝자리 색상 family를 더 진하고 선명하게 표시한다.
- 비선택 label은 같은 색상의 밝은 paper tint를 사용해 읽기 쉽게 표현한다.
- 사용자는 0~9 각 끝자리의 색상을 직접 바꾸고 기본값으로 복원할 수 있어야 한다.

## 6. 디지털 탐색 원칙

### 6.1 기본은 파일철, 검색은 렌즈

```text
기본 Home = 파일철 보기
검색/필터 = 필요한 파일철·기록지로 빠르게 가는 렌즈
```

검색과 필터는 별도의 고립된 데이터베이스 세계를 만들면 안 된다. 검색 결과를 탭하면 항상 원래 파일철 맥락으로 이동해야 한다.

```text
검색 결과
→ 해당 서랍
→ 해당 No 고객 파일
→ 해당 Today/v 기록지
→ 필요하면 해당 Paper Section
```

예:

```text
검색어: 모공

결과:
No.25 · 고객 이름
v12 · 2026.09.10
상담: 모공 및 피부결 관리 상담

선택:
→ No.25 파일철 열기
→ v12 선택
→ 상담 section으로 이동 및 강조
```

### 6.2 필수 탐색 관점

SORI는 필요할 때 아래 기준으로 같은 고객 기록을 빠르게 찾아볼 수 있어야 한다.

```text
고객 이름
전화번호
고객 No
방문 v 번호
방문 날짜
기록 키워드
고객 상태·주의사항
피부 타입/민감 정보
제공 서비스
프로그램
담당자
결제 상태
사진/Before/After
다음 방문 예정일
미기록 고객
장기 미방문 고객
VIP/주의 marker
기간
```

### 6.3 보조 보기는 맥락을 잃지 않는다

지원 가능한 보조 보기는 아래와 같다.

```text
검색 결과
키워드 보기
카테고리 보기
기간 보기
사진 보기
결제 보기
재방문 대상 보기
프로그램별 보기
```

하지만 어느 보기에서도 사용자는 다음을 잃으면 안 된다.

```text
내가 어느 고객 파일에 속해 있는가?
이 기록은 어느 날짜의 어느 v인가?
원래 파일철로 어떻게 돌아가는가?
```

## 7. Notion과의 차이

SORI는 Notion의 문서성·연결성·읽기와 쓰기가 이어지는 경험을 참고할 수 있다. 그러나 Notion처럼 사용자가 처음부터 시스템을 설계해야 하는 앱이 되어서는 안 된다.

| Notion | SORI |
|---|---|
| 사용자가 페이지·DB·속성·view를 직접 설계 | 앱이 고객 기록의 큰 틀을 제공 |
| 처음에 무엇을 만들지 결정해야 함 | 즉시 고객 파일을 찾고 기록 시작 |
| 자유로운 블록 조합 | 표준화된 Chart 구조 안에 기록 |
| 높은 자유도와 초기 진입장벽 | 낮은 진입장벽과 현장 업무 속도 |
| 범용 작업공간 | 뷰티 현장 고객 기록 운영 시스템 |

SORI의 원칙:

> 사용자는 시스템을 설계하지 않는다. 이미 잘 설계된 파일철 안에서 고객 기록을 복제하고, 쌓고, 찾고, 필요한 내용을 자연스럽게 끼워 넣는다.

## 8. 모든 UI/UX 설계 전 질문

새 화면, 새 기능, 새 컴포넌트를 만들기 전 반드시 아래 질문에 답한다.

### 8.1 현실 행동

1. 현실에서 사용자는 무엇을 집는가?
2. 현실에서 사용자는 무엇을 넘기는가?
3. 현실에서 사용자는 어디에 라벨을 붙이는가?
4. 현실에서 사용자는 무엇을 파일철에 끼우는가?
5. 현실에서 사용자는 무엇을 다시 찾는가?

### 8.2 시각적 위계

6. 화면만 보아도 서랍·파일·기록지·부속 문서의 위계가 보이는가?
7. 이 항목은 버튼인가, 파일 label인가, 종이 기록지인가, 조용한 action인가?
8. 선택된 항목이 현재 열려 있는 본문과 시각적으로 연결되는가?
9. 새 UI가 기존 화면의 문법과 일치하는가?
10. 이 구현이 Material 기본 button/chip/card/form으로 현실의 구조를 축소하고 있지는 않은가?

### 8.3 학습 없는 사용

11. 사용자가 설명을 읽지 않고 한두 번 탭해도 다음 행동을 이해하는가?
12. 사용자는 “폼에 입력한다”고 느끼는가, “기록지에 이어 쓴다”고 느끼는가?
13. 사용자는 고객 파일과 방문 기록의 관계를 즉시 알 수 있는가?
14. 화면에 새로운 버튼·카드·탭을 추가하지 않고 기존 파일철 안에 자연스럽게 넣을 수 있는가?

### 8.4 디지털 편의

15. 아날로그에서 느린 행동을 검색·필터·즉시 이동으로 한 번에 해결할 수 있는가?
16. 검색 결과는 사용자를 원래 파일철 맥락으로 정확히 돌려보내는가?
17. 키워드·카테고리·기간·사진·결제·프로그램 등 여러 관점으로 빠르게 볼 수 있는가?
18. 보조 보기로 이동해도 고객·No·v·날짜의 맥락을 잃지 않는가?

### 8.5 구현 승인

19. 실제 iOS/Android runtime에서 화면을 보고 검증했는가?
20. 작은 화면, 가로 rail, 세로 scroll, keyboard, safe area에서 overflow나 잘림이 없는가?
21. 이 화면을 실제 현장 직원에게 보여 주었을 때 설명 없이 이해할 수 있는가?

위 질문 중 하나라도 명확한 “예”가 아니면, 코드를 더 쓰기 전에 UI 구조를 다시 설계한다.

## 9. 금지 사항

아래는 SORI의 UI 언어를 훼손하므로 기본적으로 금지한다.

```text
Material Chip으로 파일/기록지를 표현
ElevatedButton, OutlinedButton을 파일 label로 사용
검정 pill CTA 남발
완전 rounded rectangle을 모든 요소에 적용
고객 이름만 있는 세로 ListTile를 고객 파일철로 사용
둥근 TextField를 세로로 연속 나열한 Chart form
필드마다 큰 shadow card
화면 중앙의 설명형 빈 상태를 기본 화면으로 사용
동의서·사진·결제를 우측 action chip 모음으로 배치
Today와 실제 오늘 v를 중복 표시
오늘 기록이 없을 때 과거 v를 숨김
검색 결과를 별도 고립 화면으로 끝냄
상단 Workspace tab과 내부 file rail을 동일한 크기·위계로 복제
코드 변경 설명만으로 UI 완료를 선언
```

## 10. 시각 검증 원칙

UI 변경은 코드 diff나 설명으로 완료되지 않는다.

필수 루프:

```text
코드 수정
→ analyze/test
→ iOS Simulator 실행
→ Android emulator 또는 실기기 실행
→ 탭/스크롤/입력/저장/복귀 확인
→ 화면 캡처
→ 이 문서와 비교
→ 불일치 수정
→ 재검증
```

각 UI milestone은 다음을 포함해야 한다.

```text
실제 화면 artifact
실행한 interaction scenario
검증한 디자인 원칙
발견한 UI 문제
수정한 파일
남은 제한 사항
```

중요한 상태별 최소 검증 화면:

```text
Desk 선택
Chart 초기 화면
고객 파일 선택
오늘 기록 없음
오늘 기록 있음
과거 v 선택
Chart section inline edit
검색 결과 → 특정 file/visit/section 이동
0~9 index palette 변경과 즉시 반영
좁은 화면 overflow 확인
```

## 11. 제품 문장

SORI는 다음 한 문장으로 이해되어야 한다.

> **현실의 고객 파일철을 꺼내 기록하고 다시 정리하는 직관은 그대로 유지하면서, 검색·분류·연결·속도는 디지털 수준으로 확장한 뷰티 현장용 고객 기록 시스템.**

SORI가 사용자에게 제공해야 하는 감각은 다음이다.

```text
아날로그의 손 감각
+ 디지털의 즉시성
+ 정해진 틀의 편안함
+ 쌓일수록 더 찾기 쉬운 기록
```

이 네 가지를 동시에 만족하지 못하는 화면은 SORI의 완성된 UI가 아니다.
