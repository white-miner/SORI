# Cursor에 그대로 붙여넣는 지시문 모음

규칙 파일은 에이전트의 "기본 성격"을 정하고, 아래 지시문은 매 작업의 "안전벨트"다. 둘 다 필요하다.

---

## 1. 작업 시작 전 — 조사만 시키기

```
조사만 해. 코드는 절대 수정하지 마.

목표: 상담차트에서 고객차트로 넘어가는 현재 흐름을 파악한다.

다음을 순서대로 출력해:
1. 관련 파일 목록과 각 파일이 하는 일 (파일당 2줄)
2. 상담 저장 시점부터 고객차트 렌더까지의 호출 체인
3. 현재 사진이 고객에 붙는 방식 (테이블/필드/코드 위치)
4. 이 흐름을 Visit 중심으로 바꿀 때 깨질 수 있는 지점 top 5
5. 각 지점의 위험도 (상/중/하)와 이유

마지막에 "수정 제안"은 하지 마. 사실만 보고해.
```

## 2. 계획 승인 단계

```
방금 조사한 내용을 바탕으로 변경 계획만 작성해. 코드 수정 금지.

형식:
- 목적
- 수정할 파일 전체 목록
- 건드리지 않을 것 (명시)
- 바뀌는 동작 / 안 바뀌는 동작
- Expand / Backfill / Contract 중 어느 단계인지
- 롤백 방법
- 검증 명령

계획을 3개 이하의 커밋으로 쪼개서 제시해. 한 커밋에 5파일을 넘기지 마.
```

## 3. 특성화 테스트 먼저

```
아직 기능은 건드리지 마.

현재 상담차트 → 고객차트 흐름의 "지금 동작"을 그대로 박제하는 테스트를 작성해.
'옳은 동작'이 아니라 '현재 동작'을 기록하는 특성화 테스트다. 버그가 있어도 그 버그를 그대로 기록해.

작성 후 실제로 실행해서 전부 통과하는 걸 확인하고, 출력을 붙여줘.
이 테스트가 앞으로 모든 변경의 안전망이 된다.
```

## 4. 실제 구현 (Expand 단계)

```
[Expand 단계만] visits 테이블을 추가해.

허용:
- 새 테이블 visits 생성
- photos에 visit_id 컬럼 추가 (nullable)

금지:
- photos의 기존 컬럼 수정/삭제
- 기존 API 응답 필드 제거
- 기존 화면 코드 수정

작업 후 npm run typecheck && npm run test 를 실제로 실행하고 출력을 붙여.
기존 테스트가 하나라도 깨지면 즉시 멈추고 보고해. 스스로 고치려 하지 마.
```

## 5. 무언가 깨졌을 때

```
멈춰. 되돌리지 말고 현재 상태 그대로 둬.

1. 어떤 테스트가 왜 실패하는지 정확히 설명해
2. 실패 원인이 되는 커밋과 코드 라인을 특정해
3. 가능한 수정 방안 2가지를 장단점과 함께 제시해

내가 고르기 전까지 아무 파일도 수정하지 마.
```

---

## 운영 습관 3가지

1. **작업 브랜치 분리.** `feat/visit-expand` 처럼 단계별 브랜치를 파고, main은 항상 동작하는 상태로 둔다.
2. **각 단계 후 수동 스모크 테스트.** `docs/CONTRACTS.md`의 6개 플로우를 직접 손으로 한 번씩 눌러본다. 3분이면 끝나고, 자동 테스트가 놓치는 걸 잡는다.
3. **에이전트에게 "왜"를 설명하게 한다.** 코드를 받기 전에 "이 변경이 기존 X를 왜 깨뜨리지 않는지 설명해"라고 물어라. 설명이 막히면 그 코드는 쓰지 않는다.
