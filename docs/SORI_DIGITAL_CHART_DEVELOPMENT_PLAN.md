# SORI 디지털 차트지 개발 계획서

작성일: 2026-09-29 · 상태: 구현 승인 전 계획

> 후속 문서: [최종 제품 기획서 v1.0](SORI_DIGITAL_CHART_PRODUCT_SPEC.md). 이 초기 계획서의 명칭·화면 구성·개발 순서는 최종 기획서로 대체한다. 최종 구간 명칭은 **기본 정보 / 문진 기록 / 상담 기록 / 관리 내용 / 변화 기록**이다.

## 1. 제품 목표와 완료 정의

디지털에 익숙하지 않은 원장이 스마트폰으로 고객을 선택하고, 지난 기록을 확인하고, 오늘 기록을 남긴 뒤 다음 방문에 다시 꺼내 볼 수 있게 한다. 에스테틱의 피부관리와 체형관리를 함께 지원하며, 피부·얼굴을 모든 방문의 기본 전제로 삼지 않는다.

주 동선은 `홈 CHART → 고객 선택 → 지난 기록 → 오늘 기록 → 완료된 기록지`다. 서랍·파일·회차 구조는 기존 기록을 찾는 보조 수단으로 유지하며, 새 기록 작성의 선행 학습 조건으로 만들지 않는다.

완료의 정의는 화면 전환이 아니다. 저장 성공 후 고객·방문·사진의 연결이 유지되고, 새로고침 또는 앱 재실행 후에도 동일 기록이 열려야 한다. 기존 저장 데이터 삭제, 기존 라우트 교체, 테이블 재설계는 이번 목적이 아니다.

## 2. 현재 코드에서 확인한 출발점

- `ChartWorkspacePage`에서 실제 고객을 바인딩하고 `ChartVisitHomePage`를 홈 CHART에 포함한다.
- `ChartVisitFlowPage`는 INFO/SKIN/CONSULT/CARE/RESULT 다섯 단계를 사용한다. 고민 선택 이후에만 피부 점수와 Before가 나타난다.
- 고민 칩, 관리 목표, 점수, 접힌 관리 상세 입력은 재사용할 수 있다.
- 새 작성기의 사진 버튼은 현재 각도 Set만 변경한다. 기존 B&A 촬영 기능과 새 작성기 버튼의 실제 연결은 별도 작업이 필요하다.
- 상담은 상태·타이머 기반 샘플이며 실제 음성을 저장하지 않는다.
- 자동저장은 600ms debounce를 사용한다. dispose에서 타이머를 취소하며 마지막 변경의 영구 보관과 저장 요청 순서 보장은 보완 대상이다.
- RESULT의 완료 버튼은 리포트 화면을 열고, 실제 완료 저장은 그 다음 고객 CHART 버튼에서 실행한다.
- 고객 안전정보와 방문 복원 코드에는 빈 문자열 또는 누락을 없음/해당 없음으로 바꾸는 처리가 있다.

위 내용은 로컬 소스 조사 결과이며 운영 배포 상태나 실기기 검증 결과가 아니다.

## 3. 다섯 구간 명칭과 역할

| 제안 명칭 | 판단 | 최종 권장 명칭과 역할 |
|---|---|---|
| 기본 정보 | 적합. 단, 재입력 폼으로 만들지 않음 | 기본 정보: 고객명·방문일·담당자 등 읽기 중심 |
| 문진 기록 | 적합. 현재 상태 확인과 고객의 말을 담음 | 문진 기록: 안전정보 확인, 오늘 고민, 원하는 변화 |
| 상담 진단 | 고객 발언과 관리사 판단을 구분하는 명칭이 적합 | 상담·상태 확인: 상담 기록, 관리 부위별 관찰, 선택적 상태 기록 |
| 관리 내용 | 최소 기록의 중심에 적합 | 관리 내용: 실제 한 관리, 순서, 필요 시 상세 |
| 변화 기록 | 사진·반응·다음 방문을 연결하기에 적합 | 변화 기록: 전후 사진, 관찰된 변화, 관리 후 안내 |

‘상담·상태 확인’은 피부와 체형에 공통으로 사용할 제품 용어다. 고객 발언/관리사 관찰/실측/AI 초안은 화면과 저장 의미를 구분한다. 좁은 화면에서 줄임이 필요하면 탐색 라벨은 ‘상담’, 펼친 제목은 ‘상담·상태 확인’으로 사용한다.

### 3.1 피부·체형을 함께 담는 공통 기록 구조

- 공통 기록은 고객·방문·관리 내용·관리 부위·전후 기록·고객 반응·다음 관리다.
- 선택한 관리 프로그램과 부위에 따라 필요한 상세 항목을 제안한다. 방문 시작 시 피부/체형 중 하나를 반드시 고르게 하는 추가 관문은 만들지 않는다.
- 같은 방문에 얼굴 관리와 복부·등·하체 등 체형관리를 함께 기록할 수 있다. 관리 종류마다 방문을 중복 생성하지 않는다.
- 고민 질문은 ‘오늘 어떤 부분이 가장 신경 쓰이세요?’처럼 중립적으로 표현한다. 피부 고민 칩은 피부관리 상세에서 제공하며 체형관리에도 강제하지 않는다.
- 피부 상세: 수분·유분·홍조 등 기존 9개 점수. 필요한 경우에만 사용한다.
- 체형 상세: 부위, 고객이 느끼는 붓기·당김·불편감, 관리사 관찰, 필요 시 둘레 등 실측. 입력하지 않은 상태를 정상 또는 0으로 간주하지 않는다.
- 실측은 수치뿐 아니라 단위·측정 부위·좌우·시점·측정 조건을 함께 식별한다. 체형 수치를 피부 점수 컬럼에 재사용하지 않는다. 구체적인 저장 확장은 별도 검토·승인한다.
- 변화는 피부·체형 모두 선택, 사진, 한 문장으로 남길 수 있다. 주관적 느낌과 실측 변화는 구분하며 사진만으로 수치나 효과를 자동 추정하지 않는다.
- 사진은 얼굴 정면/좌우에 고정하지 않는다. 선택한 부위와 방향을 사진세트로 구분하고 같은 조건의 전후 사진을 비교한다. 필요한 부위만 촬영하며 전신 사진을 필수화하지 않는다.

다섯 구간은 필수 순차 설문이 아니다. 구간별 독립 진입을 허용하고 이전/다음은 보조 이동 수단으로 둔다. 360px에서 긴 라벨 다섯 개를 같은 폭으로 강제 배치하지 않는다.

## 4. 화면 구조

### 4.1 고객 선택과 지난 기록

- 홈 CHART의 기존 고객 선택 기능을 유지한다. 선택 후 최근 관리·주의사항·지난 변화·다음 권장 관리를 요약한다.
- 주요 행동은 ‘오늘 기록’. draft가 있으면 ‘이어서 기록’과 ‘새 방문 기록’을 구분한다.
- 최신 기록을 한 번 누르면 해당 방문의 읽기 화면을 연다. 오래된 기록은 기존 타임라인/회차 탐색에서 찾는다.
- 사진이 없으면 낮은 빈 상태를 쓰고 사진이 있으면 실제 저장 URL을 표시한다. 존재 여부만으로 사진이 있는 듯한 목업을 그리지 않는다.
- 방문 선택·사진 열기·뒤로가기 후 고객과 방문 선택을 유지한다.

### 4.2 오늘 기록의 기본 화면

```text
← 김소리                 저장 상태
2026.09.29 · 오늘 기록

지난 기록 요약       펼치기
오늘 안전 확인       확인 필요 / 확인됨

오늘 한 관리
[최근 사용 관리] [관리 선택] [+ 직접 기록]

[관리 전 사진] [관리 후 사진]

달라진 점
[변화 선택] [한 줄 기록]

더 기록하기
기본 정보 / 문진 기록 / 상담·상태 확인 /
관리 내용 상세 / 변화 기록 상세

                    [기록 완료]
```

사진·변화·관리 입력은 독립적으로 접근한다. 최소 화면에서 쓴 값과 상세 구간의 값은 같은 draft를 편집하며 중복 저장하지 않는다. 자유 입력과 음성은 선택 입력을 보완한다.

고객 이름과 방문 날짜는 계속 확인 가능하게 한다. 시스템 글자 확대에서는 날짜를 두 번째 줄로 보내고 저장 상태와 겹치지 않게 한다. 하단 CTA는 SafeArea와 키보드 높이를 반영하며 마지막 콘텐츠를 가리지 않는다.

### 4.3 최초 방문과 재방문

- 최초 방문: 미확인 안전정보와 문진 기록을 먼저 안내하되 사진 촬영과 임시저장은 허용한다.
- 재방문: 지난 값과 확인 시점을 보여주고 ‘지난 정보와 같음’ 또는 ‘변경 있음’으로 확인한다.
- ‘지난 정보와 같음’은 기존에 실제 값이 있는 항목만 오늘 확인한 것으로 기록한다. 미확인 항목을 없음으로 바꾸지 않는다.
- 기록지에서 빠져나와도 작성 중 기록을 잃지 않는다. 상세 입력을 하지 않았다는 이유로 다음 구간 이동을 막지 않는다.

## 5. 최소 기록·상세 기록 규칙

| 정보 | 기본 노출 | 상세 또는 선택 |
|---|---|---|
| 고객·방문일 | 항상 표시 | 고객정보 수정 |
| 안전정보 | 확인 상태와 주의항목 | 항목별 확인·수정 |
| 오늘 관리 | 이름 또는 짧은 관리 내용 | 단계, 제품, 기기, 강도, 시간, 부위 |
| 관리 부위 | 선택한 관리에 맞는 부위 제안 | 복수 부위·좌우 구분 |
| 사진 | 전/후 촬영 진입 | 부위·각도·메모·사진세트 |
| 변화 | 선택 또는 한 문장 | 피부 점수 또는 체형 실측 등 필요한 전후 기록 |
| 상태 확인 | 펼치기 진입 | 피부/체형에 맞는 관찰·점수·실측, 미기록은 미기록으로 유지 |
| 상담 | 펼치기 진입 | 고객 발언·관찰·승인된 요약 |
| 다음 관리 | 간단한 메모 | 홈케어·권장 시점 |

임시저장은 빈 기록도 허용한다. 정식 완료는 고객과 방문이 식별되고, 실제 관리명/내용·저장된 사진·유효한 방문 메모 중 하나 이상의 기록이 있는 것을 기본안으로 한다. 상담만 한 방문이나 사진만 남긴 방문도 허용한다. 안전 미확인은 그대로 표시하고 관리 적합성을 자동 판정하지 않는다. 안전 미확인 시 완료를 차단하는 정책은 현재 요구에 없으므로 이번 범위에서 임의 추가하지 않는다.

‘관리 목표’와 ‘실제 한 관리’는 다르다. ‘진정’ 목표만 선택했다고 ‘진정 관리 시행’으로 자동 확정하지 않는다. 관리명은 기존 의미가 맞는 필드를 재사용하고, 맞지 않으면 저장 위치 승인 후 확장한다.

## 6. 지난 관리 복사

복사 버튼은 원본 방문 날짜와 복사할 내용을 먼저 보여준다. 새 방문 ID는 유지하고 이전 방문을 수정하지 않는다.

| 복사 가능 | 자동 복사·확정 금지 |
|---|---|
| 관리명·관리 단계 제목 | 오늘 안전 확인 여부 |
| 제품·기기·부위 등 참고 설정 | 오늘 피부 점수·체형 실측·불편 정도 |
| 필요 시 시간·강도 참고값 | 사진·전후 변화·이상반응 |
| 사용자가 선택한 관리 목표 | 상담 승인 상태·완료 상태·방문일 |

복사된 내용은 ‘지난 관리에서 가져옴’으로 표시하고 원장이 확인한다. 직전 기록에 값이 없으면 데모값이나 기본 제품을 채우지 않는다. 복사 직후에도 오늘 실제 시행한 관리와 다른 부분을 쉽게 수정할 수 있어야 한다.

## 7. 안전정보의 의미와 호환성

항목별 상태를 `미확인 / 없음 / 있음 / 해당 없음`으로 구분한다. 해당 없음은 임신·수유 등 적용 가능한 항목에만 제공한다. ‘있음’은 설명과 함께 기록한다.

- Customer: 현재 알려진 정보.
- Visit snapshot: 그날 가져온 정보와 그날 확인한 사실.
- 현재정보가 있다고 오늘 확인한 것은 아니다. 값과 확인 여부를 분리한다.
- 기존 문자열 snapshot 키는 유지한다. 확인 상태·확인 시각을 별도의 버전 있는 메타데이터로 추가하는 안을 우선 검토한다.
- `Map<String,String>`인 현재 safety 모델에 중첩 JSON을 그대로 넣지 않는다. 읽기/쓰기 어댑터와 모든 소비자를 먼저 점검한다.
- 과거의 ‘없음’ 문자열이 사용자 입력인지 자동 기본값인지 근거가 없으면 구분 불가로 취급한다. 과거 snapshot을 일괄 보정하거나 오늘 확인됨으로 승격하지 않는다.
- 오래된 기록에서 오늘 정보로 fallback하지 않는다. 과거 미기록은 ‘당시 기록 없음’으로 보여준다.
- 고객 현재정보 수정 실패와 방문 snapshot 저장 실패를 각각 처리한다. 일부만 성공한 상태를 전체 저장 완료로 표시하지 않는다.

빈 문자열을 없음으로 바꾸는 세 경로부터 특성화한다: `safetyFromCustomer`, `safetyFromRecord`, `ChartVisitSession.fromRecord`. `SafetySnapshot` 생성자 기본값과 CHECK 요약도 함께 점검한다.

## 8. 촬영·말하기 구현 기준

### 촬영

기존 촬영/압축/업로드 서비스를 재사용하되 현재 draft의 정확한 chart ID와 사진세트 관계를 전달한다. 날짜로 방문을 재검색해 다른 회차에 붙이지 않는다. `ChartPhotoStorage.uploadWebp` 시그니처, Storage 경로, 대표 before/after URL 계약을 유지한다.

카메라 취소는 데이터 변화 없이 복귀한다. 권한 거부는 앨범 선택 또는 권한 안내로 복구한다. 업로드 중·실패·재시도·저장 완료를 구분하고 완료 전 사진을 저장된 사진처럼 표시하지 않는다. 업로드 중 기록 완료 시에는 기다리거나 ‘사진 제외하고 완료’를 명시적으로 선택하게 한다. 예고 없이 사진을 버리지 않는다.

### 말하기

실제 음성 기능은 별도 후속 작업으로 둔다. 그전까지 운영 기록지에는 동작하는 한 줄 입력을 제공하고, 샘플 녹음 타이머를 실제 기록처럼 노출하지 않는다.

후속 흐름은 `마이크 → 녹음 상태 → 종료 → 변환 초안 → 수정/적용`이다. 변환 실패 시 음성 또는 사용자가 입력한 내용을 복구할 수 있는 보관·삭제 정책을 먼저 정한다. AI가 말하지 않은 사실을 채우거나 생성 초안을 자동 승인하지 않는다. 음성 공급자·비용·보관 기간·권한 처리는 별도 승인 범위다.

## 9. 저장·완료·재조회

- 변경 내용을 기기에 임시 보관하고 서버 저장은 debounce하되 같은 draft의 요청을 순서대로 처리한다.
- 최신 편집 버전이 저장된 경우에만 ‘서버에 저장됨’을 표시한다. 오래된 응답이 최신 상태를 덮지 못하게 한다.
- 화면 이탈/백그라운드 전환 시 보관하고 마지막 네트워크 호출 성공에만 의존하지 않는다.
- `기록 완료`는 대기 저장과 사진 상태를 정리한 뒤 completed 저장 성공 시 리포트를 연다.
- 완료 중 버튼 재탭을 막고, 지연된 draft 저장이 완료 상태를 다시 draft로 되돌리지 않게 한다.
- 리포트의 `고객 차트`는 이동만 한다. 저장 실패 시 입력 화면과 내용을 유지하고 재시도한다.
- 회원권 차감·결제·visit_checked 변경·피드백 발행은 이 완료 동작에 추가하지 않는다.
- 재조회는 서버 기록을 새로 읽는 조건에서도 확인한다. 메모리의 같은 객체가 보이는 것을 저장 성공의 증거로 삼지 않는다.
- 기기 임시보관은 고객정보이므로 계정·샵별 분리, 로그아웃 정리, 보관 기간을 정한다. 서버 완료 후에도 로컬 사본이 불필요하게 남지 않게 한다. 오프라인 영구 보관이 불가능한 환경은 그 한계를 표시한다.

## 10. 구현 단계와 변경 파일 후보

각 단계는 별도 승인·검증 단위다. 한 작업의 수정 파일은 테스트 포함 최대 5개로 제한한다. 아래는 작업 경계이며 확정 파일 목록은 해당 단계 조사 후 제출한다. 초과하면 구현 전에 더 나눈다. 기존 코드 재작성 대신 추가 컴포넌트/어댑터로 확장한다.

| 단계 | 결과물 | 주요 파일 후보 | 완료 조건 |
|---|---|---|---|
| 1A | 오늘 기록 최소 UI, 한국어 구간 탐색 | `chart_visit_flow_page.dart`, 신규 최소 기록 위젯, `chart_visit_preview_test.dart` | 고민 미선택 상태에서도 관리·사진 진입 가능 |
| 1B | 홈 고객 선택→지난 기록→오늘 기록 | `chart_workspace_page.dart`, `chart_visit_home_page.dart`, `chart_workspace_page_test.dart` | 홈 CHART 실제 입구에서 새 흐름 왕복 |
| 2A | 안전정보 상태·호환 어댑터 | `chart_visit_record.dart`, `chart_visit_mock.dart`, `chart_visit_live.dart`, 관련 모델 테스트 | 미확인/없음 구분, 옛 snapshot 불변 |
| 2B | 안전 확인 UI와 오늘 확인 메타데이터 | 안전 확인 신규 위젯, flow, 관련 모델/UI 테스트 | 재방문 확인과 변경사항 수정 연결 |
| 3A | 저장 요청 순서·완료 확정 | flow, live gateway, 신규 저장 조정자, 저장 테스트 | 저장 실패·연속 탭·완료 경합 검증 |
| 3B | 기기 임시보관과 복구 | 신규 draft 보관소, 저장 조정자, lifecycle 연결, 관련 테스트 | 종료·재실행·통신 끊김 복구 |
| 4A | 기존 촬영을 현재 방문에 연결 | 신규 사진 연결 어댑터, flow, 기존 촬영 진입부, 사진 테스트 | 실제 사진이 정확한 방문에 저장 |
| 4B | 홈·리포트의 실제 사진과 기록 재조회 | home, flow/리포트 위젯, live 변환, 관련 테스트 | 사진·관리·변화를 재실행 후 확인 |
| 5A | 지난 관리 선택 복사 | 신규 복사 어댑터, 관리 UI, 관련 테스트 | 안전·점수·사진·완료 상태 미복사 |
| 5B | 추가 기록·변화 메모 저장 보완 | record, live, 저장 어댑터, 관련 테스트 | 임의 기존 필드에 몰아넣지 않고 재조회 |
| 6 | 실제 사용자·실기기 검수 | 필요한 최소 수정만 별도 분할 | 아래 검수표 통과 후 배포 판단 |
| 후속 | 실제 말하기 기록 | 별도 계획 | 공급자·보관 정책 승인 후 구현 |

경로 기준: feature 파일은 `lib/features/chart_visit/`, record는 `lib/models/`, workspace는 `lib/views/chart_workspace/`, 테스트는 `test/`다.

1A/1B는 먼저 실제 UI를 확인하는 단계다. 이때 사진·음성 미연결 동작을 완료된 기능으로 보고하거나 운영에 노출하지 않는다. 이후 각 단계도 화면에서 생성한 값이 저장·재조회되는 것까지 확인한다. 전체를 구현한 후 한꺼번에 UI 검수하지 않는다.

## 11. 호출부 조사·보호 계약·롤백

승인 후 각 구현 작업 전에 다음 참조의 전체 검색 결과와 변경 대상 호출부를 제출한다.

```powershell
rg -n 'ChartWorkspacePage|ChartVisitHomePage|ChartVisitFlowPage|bindChartVisitRoute' lib test
rg -n 'SafetySnapshot|safetyFromCustomer|safetyFromRecord|customerSafetyPatch' lib test
rg -n 'createChartVisitDraft|saveChartVisitDraft|ChartVisitGateway' lib test
rg -n 'uploadWebp|chart_photo_records|photoSetId|beforeImageUrl|afterImageUrl' lib test
```

이번 문서는 참조 전체가 아니라 확인한 핵심 경로를 근거로 한 계획이다. 사진 등 광범위한 호출부의 전체 영향도 검사는 해당 단계의 구현 전 조건이다.

유지: `customer_charts` 한 행=한 방문, 기존 URL 컬럼, 사진세트 관계, 기존 API·라우트·저장 함수 시그니처, 고객차트 정렬 계약. 변경하지 않음: 결제·회원권·동의·우리지역·커뮤니티·기존 B&A 저장 규칙. `HomeVisualTokens`를 임의 수정하지 않고 최신 시각 기준을 따른다.

새 메타데이터가 필요하더라도 우선 기존 JSON의 의미와 소비자를 검증한다. DB 변경이 필요하면 별도 nullable 추가 계획으로 제시한다. 기존 마이그레이션 수정·삭제·rename·과거 데이터 일괄 덮어쓰기는 하지 않는다.

롤백은 단계별 커밋을 되돌리는 새 커밋 또는 새 UI 진입 비활성화로 수행한다. 새로 작성한 방문과 사진은 보존하고 기존 화면에서도 기존 필드를 읽을 수 있게 한다. 파괴적 reset이나 데이터 삭제로 롤백하지 않는다.

## 12. 검증 계획

기존 특성화 테스트로 기준 동작을 확인한 뒤 변경 동작 테스트를 추가한다. 아래는 실행 계획이며 이번 문서 작성 중 테스트를 실행한 것은 아니다.

```powershell
flutter analyze
flutter test test/chart_visit_preview_test.dart test/chart_visit_record_test.dart test/chart_workspace_page_test.dart
flutter test test/customer_chart_photo_ba_test.dart test/shoot_hub_c1_test.dart
flutter test
flutter build web --release
```

운영 빌드는 실제 workflow의 define/base-href 조건도 재현한다. 새 저장·안전정보·사진 연결 테스트 파일은 단계별 명령에 추가한다. 전체 테스트 실패는 main에서도 재현되는지 분리하고 이번 변경의 실패는 해결한다.

필수 검수:

1. 기존 고객 선택→최근 기록 확인→관리 한 개 기록→완료→앱 재실행→같은 방문 열기.
2. 고민을 선택하지 않고 Before 촬영, 취소/재시도 및 다른 회차 오연결 없음.
3. 피부 점수 9개를 입력하지 않아도 기록 가능, 체형관리에는 피부 문진을 강제하지 않음. 미기록을 0이나 기본 3으로 저장하지 않음.
4. 안전정보 빈 값은 미확인, 없음은 명시적 입력, 과거 snapshot은 변경되지 않음.
5. 마지막 입력 직후 뒤로가기/백그라운드/앱 종료 후 복구.
6. 네트워크 끊김·복구·느린 저장 응답·완료 버튼 연속 탭에서 유실/중복/상태 역전 없음.
7. 지난 관리 복사 후 이전 방문은 불변, 오늘 피부·체형 상태·실측·안전·사진은 미확정 유지.
8. 촬영 권한 거부·업로드 실패에도 다른 입력은 유지.
9. 360×800, 390×844, 태블릿 세로·가로에서 이름·날짜·버튼·사진·키보드 겹침 없음.
10. 글자 1.3배/1.5배, 긴 고객명·관리명·메모에서 핵심 조작 접근 가능.
11. 테스트 계정 전환 시 다른 고객의 로컬 초안이 보이지 않음.
12. 기록 완료가 결제·회원권 차감·동의 생성 등 기존 부수효과를 유발하지 않음.
13. 피부관리만, 체형관리만, 피부+체형 복합관리의 세 방문 시나리오를 각각 검수. 복합관리는 한 방문 안에서 부위별 기록·사진을 구분하고 같은 부위·방향의 전후 사진을 비교함.

실사용 검수 제안: 디지털에 익숙하지 않은 원장 3~5명에게 설명 없이 동일 과제를 준다. 도움 요청 횟수, 최초 행동까지 시간, 완료율, 재조회 성공률, 기록 누락을 측정한다. 목표는 기존 고객의 간단 기록을 촬영 시간을 제외하고 1분 안에, 지난 기록을 고객 선택 후 10초 안에 찾는 것이다. 이는 현재 성능 주장이 아니라 초기 제품 목표이며 관찰 후 조정한다. 검수 시나리오 내 데이터 유실·고객 오연결·중복 방문은 0건이어야 한다.

## 13. 첫 승인 범위 제안

먼저 1A만 구현한다. 피부에 한정되지 않는 한국어 구간 탐색, 최소 기록 화면, 고민 선택과 사진/상태 확인 진입의 분리를 실제 모바일 화면으로 검수한다. 기존 선택·접힘 UI와 저장 모델을 재사용하고 DB·촬영 엔진·음성 공급자는 변경하지 않는다. 이 단계에서 새 체형 실측 데이터 저장까지 완료했다고 보고하지 않는다. 체형 상세 저장은 5B의 저장 보완 범위에서 별도 매핑·승인 후 진행한다.

1A 승인 후 1B로 실제 홈 입구를 연결하고, 이후 안전정보와 저장 신뢰성을 완성한다. UI만 검수한 단계를 기능 완료나 운영 배포 완료로 보고하지 않는다.
